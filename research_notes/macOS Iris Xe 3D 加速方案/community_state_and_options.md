# Community state of GPU-accelerated macOS guests on non-Apple hosts, and options for a minimal Linux/KVM -> macOS QEMU laptop appliance (Intel Iris Xe)

Research date: 2026-11-04. Method: web search + page fetches only. I could not clone repos or query the GitHub API (session had no repo access), so **commit dates / "last commit" could not be verified for any GitHub project below**. All GitHub-README claims are self-reported by the authors; I did not run anything. Several of the key projects are very new (2026) and have little independent corroboration.

## 1. Has anyone actually gotten Metal/3D in a macOS guest on Linux/KVM, and with what?

### Takeaway
Yes, in two distinct ways. (a) Classic dGPU passthrough (VFIO) of a natively supported AMD card works and is the long-standing community answer, but it is NOT "emulating the GPU" and Iris Xe cannot be used this way (see Q4). (b) As of 2026 there is a genuinely new class of paravirtual approach: reimplementing the host side of Apple's own `AppleParavirtGPU` device (PCI `106b:eeee`) on Linux, translating Metal to Vulkan. Two projects claim working x86-64 Tahoe guests on Linux/KVM, but both are verified only on NVIDIA GPUs, are alpha/beta, and report low frame rates (~25-30 presents/s).

### Cited Findings

**A. Paravirtual (no passthrough) - new in 2026**
- **reims-vgpu (steelbrain)**: "experimental virtual GPU for macOS guests"; guest uses the stock Apple driver (no guest install); on Linux the GPU command stream is decoded and executed through Vulkan on the host GPU via "metal2vulkan"; paths: x86-64 macOS on Linux (KVM+Vulkan) and arm64 macOS on Apple silicon (HVF, Metal or Vulkan). Status "beta ... largely stabilized". Tested: Apple M3 Max (arm64 guests: macOS 13, 14, 15, 26) and an NVIDIA RTX 5080 laptop GPU on Linux (x86-64 guest: macOS 26 only). Host reqs: `/dev/kvm`, a Vulkan driver, access to `/dev/udmabuf`. Licence GPL-2.0-or-later OR LGPL-3.0-or-later. README says nothing about OpenGL; Intel/AMD/Mesa/ANV are not mentioned. No benchmark numbers given. 660 stars / 83 forks / 24 open issues / 34 open PRs at fetch time. — [reims-vgpu README](https://github.com/steelbrain/reims-vgpu); [reims-vgpu wiki](https://github.com/steelbrain/reims-vgpu/wiki)
- reims known issues on x86-64 guests: without a `METAL_ERROR_MODE=5` global-preference workaround (set from Recovery) the icon service crashes and Dock/menu bar may not appear; missing `/dev/udmabuf` access crashes at higher resolutions ("at 4K even at its desktop"); no HDR; Fn/Globe keys don't reach the guest. — [reims-vgpu wiki](https://github.com/steelbrain/reims-vgpu/wiki)
- The reims wiki lists the author's test host as "macOS 27.0.1 (build 26A434)", which is internally odd (build 26xxx is the Tahoe family) - treat the wiki's version strings with caution. — [reims-vgpu wiki](https://github.com/steelbrain/reims-vgpu/wiki)
- Earlier announcement (AMD-OSX forum, thread started 2026-09-14, author "tomnic"): translates guest Metal calls to host Vulkan using the stock `AppleParavirtGPU.kext`; claimed to work Big Sur through Tahoe but only tested on Sonoma, one 2080 Ti Linux host; author says the translation engine is "still slow"; alpha. No replies from other testers on the page. — [AMD-OSX thread](https://forum.amd-osx.com/threads/reims-vgpu-graphics-paravirtualization-for-macos.6616/)
- **qemus/qemu-macos**: a Linux QEMU build with Reims vGPU support; requires KVM, the Reims PCI device, shared memfd-backed guest RAM, **Vulkan 1.2+ host driver**, and the Reims GOP option ROM for EFI display. MIT licence; 76 commits, 3 stars, no releases, no macOS-version statement. Not mentioned: Intel Iris Xe or any specific GPU. — [qemus/qemu-macos](https://github.com/qemus/qemu-macos)
- **ultimate-macOS-KVM, branch `pvg-metal-vulkan`** (nassosyian): implements the host side of Apple's ParavirtualizedGraphics as QEMU device `pvg-linux-pci` (PCI `106b:eeee`); guest Metal command buffers replayed with **Vulkan 1.3**; AIR shaders translated to SPIR-V by an in-tree `air2spv`; guest-RAM patches ("guest fixups") work around two Tahoe-x86 Metal bugs. Experimental, "USE AT YOUR OWN RISK". Tested on **one PC: NVIDIA RTX 3060 Ti, proprietary driver, Linux and Windows 10**, one Tahoe x86_64 build. Works per README: desktop, Liquid Glass, Safari, Maps, Photos, SceneKit 3D. Measured: **~25-29 presents/s on Linux, ~22-25 on Windows 10 (WHPX)**; command buffers wait 5-9 ms in worker queue; `GPU_PERF=1` (NVIDIA PowerMizer) recovers ~1/3 of frame rate. Known limits: no argument buffers (some VFX don't draw; Blender 4.x crashes at start), shared/managed textures uploaded+written back every command buffer, occasional Metal crash in System Settings, atomics/SIMD-group/indirect draws/MSAA untested on real workloads. README says Intel/Mesa/ANV support is not mentioned (unknown). Apple's `AppleParavirtEFI.rom` is not redistributed - collected from your own guest. GPL-3.0 project, QEMU patches GPL-2.0+. README states it was authored by an AI model ("Claude Opus 5.5 (high)"). — [ultimate-macOS-KVM](https://github.com/nassosyian/ultimate-macOS-KVM); [pvg-metal-vulkan README](https://github.com/nassosyian/ultimate-macOS-KVM/blob/pvg-metal-vulkan/pvg-metal-vulkan/README.md)
- **metal2vulkan** (steelbrain; the AIR -> SPIR-V engine behind reims): Rust, "beta", needs Vulkan 1.2 device (plus `tessellationShader` for one path), Rust 1.98+, LLVM 21+ for `.ll` input; 987 commits, 306 stars; GPL-2.0+/LGPL-3.0+; names no tested GPU/driver, does not mention Intel/ANV/RADV. (A search snippet describing it as "alpha, v0.1.0" is out of date vs. the README, which says 0.2.0 is unreleased on crates.io.) — [metal2vulkan](https://github.com/steelbrain/metal2vulkan)
- **Upstream QEMU `apple-gfx-pci` / `apple-gfx-mmio`** (Phil Jordan patch series, merged into QEMU as part of the vmapple work): lets x86-64 macOS guests use Metal 3D/GPGPU, but **only on macOS hosts** because it wraps Apple's closed `ParavirtualizedGraphics.framework`. Cover letters are from late 2024-Jan 2025; I could not confirm the exact QEMU release that merged it. — [patchew v17 cover](https://patchew.org/QEMU/20250112210056.16658-1-phil@philjordan.eu); [patchew v5 cover](https://patchew.org/QEMU/20241029205819.69888-1-phil@philjordan.eu/)
- **VirtIO GPU driver for macOS** (litecreator/virtio-gpu-macos): alpha 0.1.0, README dated 2024-04-07, 3 commits, "basic 2D framebuffer functional"; **3D/Virgl not implemented** (roadmap only), cannot be Metal. — [litecreator/virtio-gpu-macos](https://github.com/litecreator/virtio-gpu-macos)
- Not paravirtual-on-Linux but adjacent: Cua (2026-08-11) shows that on Apple's Virtualization.framework (M1 Ultra host, Tahoe guest) a process-scoped Metal capability shim made llama.cpp 7-16x faster; the authors explicitly call this paravirtualization, "not true passthrough", and say it doesn't apply to VFIO/PCI assignment. Vendor-reported, one machine. — [Cua blog](https://github.com/trycua/cua/blob/main/blog/gpu-passthrough-macos-vms.md)

**B. dGPU passthrough (VFIO) - different thing from emulating the GPU**
- OSX-KVM `notes.md` documents passthrough with a tested **Sapphire RX 6600 (recommended)**, RX 570, and GT 710 (up to Big Sur) on an Intel i5-6500/Ubuntu 22.04.4 host; needs IOMMU, `vfio-pci` binding, `display=none`, VBIOS dump if "no signal", AMD reset-bug workaround, optional RadeonBoost.kext for RX 480/580/590/Radeon VII. The page has no Sequoia/Tahoe notes and states "Modern NVIDIA GPUs are supported on HighSierra but not on later versions of macOS". — [OSX-KVM notes.md](https://github.com/kholia/OSX-KVM/blob/master/notes.md); [OSX-KVM README](https://github.com/kholia/OSX-KVM)
- Proxmox forum, Sequoia + RX 6600 XT: GPU passes through, Apple logo shows, then **black screen/hang**; a Ventura + RX 6600 thread has the same "display goes off after Apple logo" symptom. I found **no confirmed Sequoia/Tahoe + Navi passthrough success** in these results. — [Proxmox: Sequoia RX 6600 XT](https://forum.proxmox.com/threads/macos-sequoia-rx-6600-xt-passthrough-boot-logo-black-screen.160854/); [Proxmox: Ventura fails](https://forum.proxmox.com/threads/macos-ventura-on-proxmox-8-but-fails-gpu-passthrough-display-goes-off-after-apple-logo.137949/)
- `wlfogle/proxmox-macos` (Tahoe 26.5.1, Proxmox VE 9.2.3, Ryzen 5 3600, RX 580): GPU enable step exists (`--enable-gpu`, `vga: none`) but **passthrough result and Metal not demonstrated**; 15 commits, 0 stars. Not evidence of success. — [proxmox-macos](https://github.com/wlfogle/proxmox-macos)
- `mickys/kvm-tahoe-nvidia`: Tahoe 26.7.1 on KVM (Ryzen 9 3950X host), **RTX 4090 passed through using a third-party "nullmoth" NVIDIA Metal driver 2.4.3**; claims Metal 3, 4K desktop, 948 GB/s VRAM bandwidth measured, 16/16 self-tests; notes software-path windows 21->34 updates/s after a desktop patch. It is described as "an experiment", single author, ships no Apple software, and states macOS's licence "allows it to run only on Apple hardware". Only evidence I found of non-AMD dGPU Metal on Tahoe. — [kvm-tahoe-nvidia](https://github.com/mickys/kvm-tahoe-nvidia)
- Dortania: nothing in macOS supports NVIDIA past High Sierra for acceleration (general community knowledge; Dortania GPU guide is the standard reference, I did not re-fetch the AMD compatibility table). The long-standing community consensus that Polaris/Vega/Navi (RX 5000/6000) are the natively supported AMD families is consistent with OSX-KVM's choice of RX 6600 but was not re-verified against a 2026 source.

### Inferences
- Paravirtual Metal-over-Vulkan on Linux is real in 2026 but very young: all three data points (reims, qemu-macos, pvg-metal-vulkan) are NVIDIA-only, Tahoe-x86-only for the Linux host path, and ~25-30 presents/s. Quality is "usable desktop, not smooth", and shader/feature gaps (no argument buffers) imply many apps will fail.
- reims and pvg-metal-vulkan appear to implement the same idea independently (reims is the earlier public announcement, 2026-09-14 forum post; the pvg README shows no date). They share the PCI ID and the stock-kext approach, so whichever matures could be adopted rather than rewritten.
- AMD passthrough to Sequoia/Tahoe has no verified recent success in what I found; black-screen-after-logo reports on Navi 23 under Proxmox are common. Treat as "works historically up to Ventura/Sonoma with RX 5000/6000 on well-behaved boards; Sequoia/Tahoe unverified".

- No Reddit (r/hackintosh, r/macOSVMs, r/VFIO), HN, Mastodon, YouTube, tonymacx86/InsanelyMac results fetched directly (search tool returned mostly mirrors/snapshots; one mirror host was blocked). Independent third-party confirmation of reims/pvg results: none found.
- The exact QEMU version that merged apple-gfx not confirmed.

## 2. Current QEMU/OSX-KVM/OpenCore status for Sequoia/Tahoe guests on Intel hosts; display devices; software-rendering expectations

### Takeaway
OSX-KVM itself (23.8k stars, 45 commits on master) is effectively stale for Sequoia/Tahoe: its docs list Sonoma as "RECOMMENDED", and say the VM "lacks graphical acceleration". Display paths for the unaccelerated case are `vmware-svga` (Ventura fix) with OVMF/OpenCore resolution matching; Tahoe is described by community members as noticeably sluggish without acceleration. I found no quantitative benchmark of CPU-rendered Tahoe.

### Cited Findings
- OSX-KVM installer menu goes High Sierra -> Tahoe but README text says "OpenCore + Monterey + Ventura + Sonoma", Sonoma "RECOMMENDED", and "the VM lacks graphical acceleration"; Ventura+ needs AVX2; known gaps: no reliable sound, no USB3. No explicit Sequoia/Tahoe notes. It says the user is responsible for understanding the Apple EULA. — [OSX-KVM](https://github.com/kholia/OSX-KVM)
- `notes.md`: switching to `vmware-svga` reportedly fixed Ventura's resolution problem (predefined resolutions otherwise gave a black screen); recovery by deleting WindowServer prefs; OpenCore `Resolution` must match OVMF "Preferred Resolution" (default 1024x768); Sonoma needs CPU model `Haswell-noTSX` instead of `Penryn`. No mention of VGA/ramfb/virtio-vga for macOS. — [notes.md](https://github.com/kholia/OSX-KVM/blob/master/notes.md)
- Other guides: `wlfogle/proxmox-macos` claims Cascadelake-Server CPU model is "30-44% faster than -cpu host" (cited to external guide, not measured); disables AVX-512/TSX/PCID; `+invtsc` required on AMD. — [proxmox-macos](https://github.com/wlfogle/proxmox-macos). OSX-PROXMOX supports Sequoia (README lists High Sierra-Tahoe in its title) and notes working TSC required since Monterey. — [OSX-PROXMOX](https://github.com/luchina-gabriel/OSX-PROXMOX)
- AMD-OSX forum (VMware-based, similar principle): "the VM doesn't have any graphics acceleration ... it will feel slow, Tahoe especially"; Broadcom reply: VMware SVGA "doesn't support 3D acceleration for macOS guests"; OC4VM discussion reports mixed results with VMware paravirtual graphics on old Macs. — [AMD-OSX post](https://forum.amd-osx.com/goto/post?id=43666); [Broadcom thread](https://community.broadcom.com/vmware-cloud-foundation/discussion/sequoia-graphics-configuration-not-supported-again); [OC4VM #95](https://github.com/DrDonk/OC4VM/discussions/95)
- The kvm-tahoe-nvidia repo reports a patched software path ("CPU-drawn windows") going from 21 to 34 full-screen 4K Safari updates/s, i.e. unpatched CPU-drawn 4K is ~21 updates/s on that setup (Ryzen 9 3950X with a GPU present, so not directly comparable). — [kvm-tahoe-nvidia](https://github.com/mickys/kvm-tahoe-nvidia)
- Tahoe (macOS 26) is the last macOS release for Intel Macs; macOS 27 is Apple-silicon only. Hence Intel-hardware (and x86 Hackintosh/OpenCore) support ends with Tahoe security updates. — [Tom's Hardware](https://www.tomshardware.com/software/macos/macos-tahoe-is-the-last-release-for-intel-macs-apple-silicon-exclusivity-will-mark-end-of-hackintoshes); [Six Colors](https://sixcolors.com/post/2025/06/macos-tahoe-is-the-last-release-to-support-intel/); [AppleInsider on OpenCore](https://appleinsider.com/articles/25/06/17/opencore-and-hackintosh-are-sadly-dead-after-apple-ends-intel-mac-support)

### Inferences
- The "AppleParavirtGPU absent => CPU Metal" question: I did not find a source characterising the macOS fallback path (e.g. `MTLSimDevice`/software renderer, CoreAnimation CPU compositing). Evidence is only indirect: pvg README notes it needs the guest `AppleParavirtGPU.kext` and Tahoe-x86 Metal bugs patched in guest RAM; kvm-tahoe-nvidia talks about "CPU-drawn windows". Expect (inference) that without any Metal device Tahoe's WindowServer composites on CPU, with transparency/Liquid Glass effects costing most; usable for terminals/browsers at 1080p, poor for video/animation.
- Long-term: a Tahoe-only, no-future-versions target is stable (no moving target), which actually favours a small appliance project.

### Gaps
- No measured software-rendering numbers for Sequoia/Tahoe on QEMU/KVM; no verified statement on which of vmware-svga / VGA / ramfb / virtio-vga work on Tahoe (only the Ventura vmware-svga note, and that virtio-gpu macOS driver is 2D alpha and macOS-host-built).
- Could not verify OSX-KVM's last commit date or issue tracker state for Sequoia/Tahoe.
- Video decode behaviour (VideoToolbox without GPU) not researched.

## 3. Is Iris Xe usable at all? Best fallback if not?

### Takeaway
No for native or passthrough: Apple ships no driver for Xe-based iGPUs (Tiger Lake and later), so passing the Iris Xe into the guest gives no Metal. The only way to use the Xe GPU is indirectly, as the Vulkan device behind a host-side paravirtual GPU, which nobody has demonstrated on Intel yet.

### Cited Findings
- Dortania GPU Buyer's Guide: Xe-based iGPUs (Tiger Lake/Rocket Lake "UHD Graphics for 11th Gen", "Intel Xe Graphics"; Alder Lake etc.) have "no support in any version of macOS"; Highest supported OS: None. — [Dortania Intel GPUs](https://dortania.github.io/GPU-Buyers-Guide/modern-gpus/intel-gpu.html)
- Community reports (search summary of r/hackintosh and Framework forum): Tiger Lake Hackintoshes boot without acceleration; Iris Xe cannot be spoofed as Iris Plus; a "custom Tiger Lake kext" GitHub project is early-stage and unverified. — [Dortania](https://dortania.github.io/GPU-Buyers-Guide/modern-gpus/intel-gpu), [Framework community](https://community.frame.work/t/macos-on-framework-laptop/2957)
- Host requirement of the paravirtual projects is only a Vulkan 1.2/1.3 driver: reims/qemu-macos "Vulkan 1.2+", pvg-metal-vulkan "Vulkan 1.3". Intel Mesa ANV on Iris Xe provides Vulkan 1.3 (general knowledge, not source-checked here). Neither project documents Intel testing. — see Q1 sources
- Fallback (software rendering) details: see Q2.

### Inferences
- Xe via paravirtual path is plausible on paper (ANV is Vulkan 1.3-capable) but untested; risks specific to Intel: shared system memory/udmabuf zero-copy behaviour, Vulkan feature gaps used by metal2vulkan (unknown which extensions), and a 96-EU iGPU being slower than the RTX 3060 Ti that only reaches ~25-30 presents/s - though the stated bottleneck is the executor pipeline latency (5-9 ms queue) rather than raw GPU speed, so an iGPU may not be much slower for a desktop workload (speculation).
- Best verified fallback today: CPU/software-rendered macOS with vmware-svga or OVMF GOP framebuffer; accept 1080p, reduce transparency/motion, no video acceleration guarantees.

### Gaps
- No report of reims/pvg-metal-vulkan on Intel/AMD iGPU or Mesa; no benchmarks of Iris Xe as Vulkan backend.

## 4. Ranked approaches, effort, risk, and legal notes

### Takeaway
Rank: (1) ship software rendering now, (2) track/adopt reims-vgpu/pvg-metal-vulkan and test it on Iris Xe/ANV as an optional accelerated mode (highest payoff per effort), (3) discrete AMD passthrough only if a laptop with a muxless/MUX dGPU is acceptable (it is not for the stated Iris-Xe-only hardware), (4) run on a Mac host, (5) write your own host-side PV GPU - not recommended because (2) already exists.

### Cited Findings (legal facts)
- Apple's macOS licence text (Section 2): single-copy licence is for "a single Apple-branded computer"; Mac App Store licence allows up to two additional virtual instances "on each Apple-branded computer you own or control that is already running the Apple Software" for development/testing/personal non-commercial use. Section N: "No Reverse Engineering" (no decompile, reverse engineer, disassemble, derive source, modify or create derivative works) - the PDF at this URL listed Sequoia as the oldest-named release, so it may be the wrong revision for Tahoe; check the current Tahoe licence. — [Apple macOS SLA PDF](https://www.apple.com/legal/sla/docs/macOSTahoe.pdf)
- Psystar: 2009 N.D. Cal. summary judgment found Psystar (a commercial seller) violated copyright and DMCA 1201 anti-circumvention; Supreme Court declined review in 2012. Does not directly settle personal-use VMs on non-Apple hardware; sources disagree on whether the EULA itself was adjudicated. — [AppleInsider](https://appleinsider.com/articles/09/11/14/apple_earns_key_legal_victory_against_psystar); [Bloomberg](https://www.bloomberg.com/news/articles/2009-11-13/apple-crushes-clone-maker-in-court); [The Register](https://www.theregister.com/2011/09/29/court_denies_final_psystar_plea/)
- Existing projects avoid redistributing Apple binaries: kvm-tahoe-nvidia fetches Apple recovery images by script; pvg-metal-vulkan requires collecting `AppleParavirtEFI.rom` from your own guest; reims downloads installers on demand. OSX-KVM tells users to understand the EULA. — [kvm-tahoe-nvidia](https://github.com/mickys/kvm-tahoe-nvidia); [pvg README](https://github.com/nassosyian/ultimate-macOS-KVM/blob/pvg-metal-vulkan/pvg-metal-vulkan/README.md); [OSX-KVM](https://github.com/kholia/OSX-KVM)
- Licences of reusable code: reims/metal2vulkan GPL-2.0+ or LGPL-3.0+; qemu-macos MIT; pvg-metal-vulkan GPL-3.0 (QEMU patches GPL-2.0+). — links in Q1
